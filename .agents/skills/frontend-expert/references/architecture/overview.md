# ReactWP Frontend Architecture

## When to Use This Reference

Read before changing application structure, routing, templates, shared runtime code, rendering, loading, or build boundaries. For page-level component and SCSS organization, also read `components-and-styles.md`.

## Source of Truth

ReactWP separates authored source from generated runtime output:

```text
configs/   Node dependencies, Webpack configuration, scripts, and tests
src/       authored WordPress, PHP, React, SCSS, and media source
dist/      generated WordPress installation and compiled assets
```

Edit `src/` and `configs/`. Never hand-edit `dist/`; builds may replace it at any time. Run npm commands from `configs/`.

The integrated frontend lives primarily under:

```text
src/themes/reactwp/
|-- js/
|   |-- App.jsx                    Browser application and React Router
|   |-- components/                Reusable presentation/interaction primitives
|   |-- inc/                       ReactWP client runtime and extension points
|   |-- render/server.jsx          Universal static/server renderer
|   `-- templates/                 Route-level, lazy-loaded page templates
|-- medias/                        Authored media copied to theme assets
|-- scss/                          Global and template styles
`-- template/                      WordPress theme PHP shell
```

## Integrated Request Flow

```text
WordPress request
  -> RouteResolver resolves the WP object and ACF data
  -> RenderStrategy chooses client/static/server behavior
  -> Bootstrap builds site/theme/system/assets/navigation/route data
  -> header.php emits safe JSON in #reactwp-bootstrap
  -> InitialRender returns empty, static, or server HTML in #app
  -> App.jsx parses Runtime, preloads the template, then creates or hydrates React
  -> TemplateRegistry resolves the route template
  -> the template receives normalized route and shared bootstrap props
```

The PHP payload and JavaScript `normalizeRoute()` together form the route contract. Page components should consume that contract, not query WordPress global state or scrape DOM generated by PHP.

## Browser Application Layers

### Application shell

`App.jsx` owns router creation, hydration vs client mounting, route context, document metadata, and the selected template. `AppShell.jsx` owns shared header/body/footer composition.

Change these only when behavior truly spans the whole application. A page-specific layout belongs in a template or component.

### Templates

Files in `js/templates/` are route-level boundaries. They:

- receive `route`, `site`, `theme`, `system`, `navigation`, and `currentUser`;
- compose sections and reusable components;
- may import template-specific SCSS so Webpack associates styles with the lazy route chunk;
- must work in the render modes configured for them;
- should not create an independent router, global loader, or scroll engine.

### Components

Files in `js/components/` are reusable UI primitives. Keep them independent of a single route's ACF field names when reuse is real. Components may accept normalized content and semantic options; templates adapt raw route data to those props.

### Runtime (`js/inc/`)

The runtime owns cross-route infrastructure:

- bootstrap normalization and route keys;
- template registration and lazy loading;
- route fetching and memory caching;
- client navigation and document metadata;
- critical/deferred resources and loader state;
- page transition sequencing;
- smooth scrolling and scroll locking;
- universal render support.

Do not put project-specific section styling or one-off animations into runtime modules. Use the `inc/config/` functions or a component-scoped lifecycle unless the behavior must govern every route.

## Client Navigation Flow

```text
AppLink / internal anchor
  -> React Router attempts navigation
  -> useRouteTransition blocker captures a different route key
  -> Scroller locks at the current position
  -> RouteService fetches and normalizes the next route
  -> Loader preloads its template, critical fonts, and critical media
  -> PageTransitionAnimation.leave() runs
  -> router proceeds after critical readiness
  -> currentRoute switches and React renders the template
  -> RouteReadySignal marks the route ready
  -> Loader reveals critical media / completes loader state
  -> target scroll position is restored, scroller unlocks
  -> PageTransitionAnimation.enter() runs
  -> deferred media begins/displays
```

Preserve this order when customizing transitions. Bypassing it can reveal an unloaded route, leave scroll locked, animate detached elements, or resolve the loader before React commits.

Same-route hash changes are not full route transitions. They use the existing `Scroller` after the target is available.

## Render Modes and Universal Constraints

Template registry entries configure one of:

- `client`: browser creates the route markup;
- `static`: build-time renderer creates HTML, browser hydrates it;
- `server`: optional Node service creates request-time HTML, browser hydrates it.

Shared template render output must be deterministic:

- no direct `window`, `document`, `localStorage`, viewport measurement, random value, or current timestamp during render;
- no content branch that differs between server and the browser's first render;
- browser-only libraries must load inside a client effect/lifecycle or a guarded dynamic import;
- invalid HTML nesting and unstable list keys can become hydration failures;
- the same template registration and `assetKey` must be visible to browser and server builds.

Effects do not run in the server renderer. Essential content and semantic structure must exist without them.

## Safe Extension Points

Prefer these files for application customization:

| Need | Extension point |
| --- | --- |
| Add or configure route template | `js/inc/config/configureTemplateRegistry.js` |
| Customize initial/route loader motion | `js/inc/config/configureLoader.js` |
| Customize global leave/enter transition | `js/inc/config/configurePageTransition.js` |
| Add a page composition | `js/templates/<Name>.jsx` |
| Add a reusable UI primitive | `js/components/<Name>.jsx` |
| Add global foundation styles/tokens | `scss/default.scss` and `scss/inc/` |
| Add route-specific styles | import a file from its template/component graph |
| Add authored media | `medias/images`, `videos`, `audios`, `fonts`, or `others` |

Change core runtime code only when the contract itself needs to change, and then update focused tests.

## Data and Trust Boundaries

- `#reactwp-bootstrap` is JSON encoded by PHP with HTML-sensitive characters escaped. Keep it data-only.
- Public route data and SEO are normalized, bounded, and stripped of non-public WordPress object references by `PublicPayload`; this is not blanket HTML, URL, or business-schema sanitization. UI sinks still require their own safe rendering and protocol contracts.
- Render unchanged backend-sanitized HTML through a small explicit `dangerouslySetInnerHTML` boundary. Use `RichText` only when its allowlisted React-tree transformations are required, and use `sanitizeDomProps` when passing flexible properties to DOM nodes.
- Use `AppLink`/`Button` for destinations so internal, external, hash, target, and prefetch behavior remains consistent.
- Do not expose REST nonces, preview tokens, secrets, or authenticated payloads in URLs or persistent client caches.
- Cache scope `public` vs `private` is a server-render cache contract, not a visual state.

## Architecture Decision Guide

Put code in the narrowest layer that owns its lifecycle:

- one section on one page -> template-local section/component;
- repeated visual pattern across routes -> shared component;
- repeated styling value -> token or shared SCSS primitive;
- route-wide composition -> template;
- every-route shell -> `AppShell`;
- navigation/loading/render contract -> runtime/config extension;
- WordPress content resolution -> PHP runtime, outside this frontend reference.

Avoid abstraction based only on similar markup. Abstract when components share meaning, behavior, states, or change cadence.

## Verification by Layer

- Template/component/SCSS: `npm run build:themes` plus visual/responsive interaction checks.
- Loader, transitions, Scroller, or animation lifecycle: `npm run test:render` and the focused animation lifecycle test.
- Registry, render modes, or server renderer: `npm run test:render` and exercise both client mount and hydration.
- Build configuration or multiple WordPress targets: `npm run build`; use production commands when optimization/manifests are affected.

Run commands from `configs/`.
