# Frontend Inspirations

## When to Use This Reference

Apply when the user provides Awwwards pages, live sites, screenshots, moodboards, brands, or descriptive art direction. This file is also the persistent project board where Awwwards URLs can be added between tasks.

References communicate ambition and design principles. They are not implementation specifications and do not authorize copying protected identity, copy, illustrations, photography, code, or a distinctive composition wholesale.

## Reference Authority and Human Specificity

When references are active, they are design evidence alongside the user's goal, the project's established visual language, real content, supplied brand assets, accessibility/performance requirements, and explicit rationale. These sources outrank generic anti-pattern checklists. The guidance below diagnoses unsupported defaults; it does not ban a familiar device that the project or a matching reference genuinely needs.

- Every major area in the selected scope must be traceable to a directly observed reference principle, a product/content requirement, the established project language, or a deliberate original decision recorded in the influence map. Header and footer require separate rows when the scope includes persistent shell design; a component-only study does not need unrelated shell analysis.
- Extract section architecture, spatial relationships, surface/container strategy, typography, media behavior, density, pacing, responsive transformation and interaction—not only palette, border radius, shadows, or animation flavor.
- Preserve the references' level of confidence. Direct observations can drive decisions; inferences must remain labelled and must not become invented implementation facts.
- Start from the supplied content, images, people, places, proof and actions. Human-feeling design comes from specificity, editorial judgment, meaningful variation and a visible relationship between form and content—not simulated randomness, fake imperfections, decorative handwriting, or arbitrary asymmetry.
- If the selected references use open editorial planes, full-bleed media, lists, rows, bands, split compositions, overlaps, typographic navigation, tables, timelines or other structures, preserve those meaningful relationships instead of flattening them into interchangeable cards. Cards remain valid where their content boundary, interaction, project system, or matching evidence earns them.
- Do not assume that replacing cards with indexed rows, label rails, pseudo-code, divider grids, boxed flows, capsule CTAs, or technical page chrome makes a result authored. Extract how the reference handles annotation, sequence, actions, navigation, transitions, process, technical information, and the final page gesture, including where it deliberately leaves content unlabelled or unenclosed.
- Record negative evidence. If the active references consistently avoid pretitles/uptitles/kickers, visible labels, item numbers, badges, standalone trailing emphasis/fact lines, code-like identifiers, equal panels, divider systems, or stylized button families, that absence is part of their design grammar and must influence this project. Do not import those devices from a remembered SaaS/agency template merely because the references leave space open.
- Treat every prominent custom graphic or illustration as first-class art direction. Record what it contributes, which real project/content/brand fact and inspected reference principle drive it, how it relates to adjacent copy/media, and why its medium is appropriate. Do not invent an abstract visual merely because a layout has empty space.
- Extract the reference's media rhythm across the whole page: when media leads, supports, disappears, becomes full-bleed or near-viewport, interrupts text, creates a transition, or leaves deliberate quiet. Apply those relationships to supplied and planned project media; do not reduce them to thumbnail cards or omit them because final assets have not arrived.
- If no reference meaningfully supports a decision, make the smallest project-specific original choice and record it. Do not fill the gap with the default visual grammar of rounded cards, gradient blobs, icon circles, tiny uppercase labels, decorative numbers, technical-looking pills, generic arrow buttons, and vague marketing copy.

The implementation must remain original, but originality is achieved by transforming observed principles around this project's real identity—not by discarding the references and falling back to generic components.

## Evidence Weighting and Context Matching

Treat reference evidence as scoped, not transferable by mere resemblance. Seeing a device once does not authorize it everywhere. Before a reference principle drives a local decision, compare:

| Evidence dimension | Required match | Invalid shortcut |
| --- | --- | --- |
| Role and content type | The observed device solves the same navigation, editorial, object, state, comparison, proof, action, or data problem | A project-card tag becomes a label above every section |
| Frequency and density | Local repetition is comparable to the observed page or is reduced with a documented reason | One observed capsule licenses a site-wide pill system |
| Scale and adjacency | The device has a similar relationship to nearby copy, media, whitespace, and other controls | A small utility control is enlarged into the hero's visual idea |
| Interaction and state | Hover, focus, click/tap, scroll, loading, and active behavior serve the same purpose | A decorative hover is copied onto every button or image |
| Responsive transformation | The local mobile/touch behavior follows an observed principle or a documented accessible adaptation | Desktop behavior is simply compressed or its evidence is assumed to cover mobile |
| Whole-page proportion | The decision preserves the reference's balance among open space, text, media, surfaces, and controls | A rare reference device becomes the dominant page grammar |

Choose a small set of driving references by area instead of treating all inspected sites as one bag of motifs. Name one primary reference whose system resolves contradictions and restrict each secondary reference to one or two explicit roles. Stop expanding the pool when the active set is sufficient or the user has locked it. Contradictory evidence is resolved by the project's content, primary job, and primary reference—not by selecting whichever screenshot permits a preferred component. Record inference separately from observation. If the only support is that a device exists on an unrelated page, role, or state, mark it unsupported.

Do not inherit information architecture by visual association. A one-page reference, case-study route, editorial index, or horizontally scrolling portfolio may teach typography, composition, media behavior, hover, transition, or scroll choreography without authorizing the same route model or page sequence. Record architecture separately in the influence map and preserve the target project's real routes, content jobs, and CMS needs unless the user explicitly changes them.

## Comparing an Existing Implementation

When references are being used to improve a current page, capture the current rendered experience before changing source. Inspect the same representative desktop and mobile viewports, complete scroll journey, shell states, and interactions that will be used for the target review.

Create a compact baseline that records:

- first-viewport hierarchy and the primary carrier of attention;
- section sequence and, for each major region, whether text, supplied/pending media, a real artifact/data view, or interaction carries the meaning;
- media count/status, displayed scale, crop and placement across the page;
- repeated wrappers and interface-device families, including their density by region;
- display/body type relationships, line measure, section heights, whitespace and pinned/sticky behavior;
- header entry/scrolled/menu states and footer transition/content/final gesture.

Then maintain one delta ledger through implementation:

| Local region | Current rendered evidence | Driving reference evidence in the same role/context | Decision (`keep`, `transform`, `remove`, `replace with supplied/pending media`) | Required visible result | Final verification |
| --- | --- | --- | --- | --- | --- |
| Example hero | Text plus generic decorative system graphic dominates | Inspected reference lets real project media carry the second focal point | Replace with pending project media | Stable large media slot and simpler hierarchy at desktop/mobile | `PASS`, `FAIL`, or `UNVERIFIED` with evidence |

The delta ledger is a decision tool, not a post-hoc explanation. Complete it before layout hardens and update it when implementation evidence changes the decision. The target is not maximum difference: preserve what is already project-specific and effective. However, a `transform`, `remove`, or `replace` row cannot pass if only the selector name, palette, radius, font, or animation timing changed.

Also create a primary-carrier map for the page. Each major section names the thing doing the communicative work: content/typography, real or pending media, a genuine product/editorial artifact, meaningful data, or interaction. Allow deliberate quiet and text-only passages, but redesign a long run of text plus interchangeable abstract filler when the selected references instead rely on concrete subjects, artifacts, or large media transitions. Do not impose an image quota.

## Inspecting a Reference

When browsing or image inspection is available, evaluate the live site at desktop and mobile rather than relying on an Awwwards thumbnail, screenshot, description, or earlier notes. A live site can change at any time.

## Proportional Reconnaissance

Choose the smallest scope that can support the design decision before browsing. Existing notes may accelerate a later pass; refresh the evidence when the live reference, affected scope, or required state may have changed.

| Scope | Required coverage |
| --- | --- |
| **Site-wide** | Inventory the complete public experience, distinct templates, persistent shell, full homepage journey, representative responsive states, and relevant transitions/interactions. |
| **Page-level** | Inspect the relevant page from top to bottom, its persistent header/footer context, representative responsive states, and only adjacent templates or transitions that materially affect that page. |
| **Component-level** | Inspect the component, immediate layout context, meaningful variants, input states, and responsive/interaction behavior. Do not inventory unrelated routes or shell states. |

Record the chosen scope, inspection date, final URL, viewports/input modes, consent/region/language state, and every relevant blocked or untestable state as `UNVERIFIED`. A supplied screenshot may be sufficient evidence for a static visual detail, but not for interaction, responsive, route, or lifecycle claims it cannot show.

### 1. Build coverage appropriate to the scope

For site-wide work:

1. enumerate primary and overlay navigation, dropdowns, footer links, prominent in-page directories, and the public sitemap when available;
2. identify first-party public routes, unique templates, content types, special landing pages, and exposed states;
3. visit every finite editorial/marketing page and every distinct template;
4. for a large generated catalog, archive, blog, or search space, inspect the listing, pagination/filter behavior, every unique template, and representative entries for meaningful variants; record the bounded sampling;
5. record authenticated, broken, geo-restricted, consent-blocked, or otherwise untestable routes as `UNVERIFIED`.

For page-level work, inspect the complete target page and the shell/adjacent states needed to understand it. For component-level work, test the component deeply once and verify its meaningful variants in immediate context. Do not claim broader coverage than was performed.

### 2. For site-wide scope, perform the homepage deep pass

For site-wide work, inspect the homepage as a complete experience, never only as a hero screenshot:

1. load or reload from a clean entry and observe the preloader, initial reveal, cursor, header, cookie layer, and first interactive state;
2. scroll deliberately from the very top to the bottom, section by section, then revisit the top when reverse-scroll or sticky behavior may differ;
3. observe every entrance/exit, scrub, pin, parallax, mask, clip, scale, color/theme, typography, media, background, sticky, and header/navigation transition;
4. pause where scroll velocity or dwell time changes behavior; test slow, normal, and faster scrolling when safe;
5. reach and inspect the complete footer, end-of-page transition, back-to-top behavior, and any route-transition affordance;
6. repeat the meaningful pass at desktop and mobile/narrow width, plus an intermediate width when the composition changes substantially.

Do not declare the homepage inspected for site-wide work if the page was not scrolled through its complete length or if major relevant interactions remain untested. Page- and component-level work need not add an unrelated homepage pass.

### 2a. Inspect header and footer when the scope includes persistent shell

Do not finish shell reconnaissance with only “header seen” and “footer reached.” For every active reference that may influence the shell, record separate evidence. Skip this subsection for a component-only study whose decision cannot affect or depend on the shell.

For the header, inspect and record:

- logo/identity scale, placement and relationship to the grid and first-screen content;
- navigation architecture, labels, grouping, active state, utilities and CTA priority;
- initial, scrolled, hidden/revealed, sticky/fixed, transparent/solid and theme-inverted states;
- link/logo/button hover and focus behavior;
- hamburger or menu trigger geometry, open/close choreography, overlay/panel composition, focus containment/restoration, Escape and outside-click behavior;
- mobile hierarchy, tap targets, viewport-height handling and what is intentionally removed or reordered.

For the footer, inspect and record:

- how the preceding section transitions into it and whether the footer feels like continuation, contrast, reveal, takeover, index, utility area or deliberate quiet;
- depth, grid, negative space, typography, media, logo/brand gesture and visual focal point;
- navigation, contact, address, newsletter, social, legal, locale and back-to-top roles actually present;
- link/media hover and focus behavior, scroll or route-transition interaction and any final motion;
- mobile reading order, grouping, collapsed/disclosed content, spacing and end-of-page behavior.

Select a header-driving reference and a footer-driving reference from the active inspected set; they may be the same or different. Record the exact observed principle being transformed, not only the site name. If no active reference provides useful evidence for one area, document the project-specific decision and why it is more appropriate than importing a generic pattern.

Capture desktop and mobile observations for both areas. If a header/footer is shared across many routes, test it deeply once, then verify route/theme/content variants rather than assuming the homepage state covers them all.

### 2b. Analyze affected preloaders, first reveal, and page transitions

Treat loading and navigation continuity as first-class composition when they are part of the selected scope or materially affect the studied page/component. Record whether each relevant mechanism exists, is deliberately absent, or could not be verified; do not manufacture a transition audit for a static component decision.

For site-wide or lifecycle-focused work, test the preloader and first reveal through:

- a cold or newly isolated first entry when tooling permits, then warm-cache reload and repeat visit;
- direct entry to the homepage and at least one representative secondary template;
- the first server/browser frame, loader background/mark/media/text, font appearance, progress feedback, wait behavior, exit, and the first fully readable page frame;
- whether content or shell appears beneath the cover, whether fallback typography or unstyled content flashes, and whether layout moves when fonts/media settle;
- desktop and mobile/touch, plus reduced motion, slow loading, cached/instant readiness, and failure behavior when safely observable;
- accessibility consequences: whether the loader blocks interaction/focus, exposes meaningful status, remains decorative, or risks trapping the route.

If the loader contains text, observe whether it is visible immediately, appears only after its font, swaps faces, shifts layout, or enters through opacity, mask, clip, transform, split text, or another treatment. Record the visual fact without guessing the font-loading code.

Test page transitions by following safe internal links between at least two materially different template pairs when the site provides them, then use browser back and forward. For each direction, record:

- trigger feedback and whether leave begins before or after navigation/readiness;
- outgoing-page treatment, persistent header/menu/cursor/loader layers, background/theme continuity, and scroll locking;
- the wait or overlap interval, route/media preparation cues, and whether a blank, stale, or mixed frame appears;
- DOM/content swap moment as observed, incoming reveal order, scroll top/restoration/hash behavior, focus/orientation, and when interaction becomes available;
- duration/easing character, masks/curtains/shared media/type movement, direction-aware variants, and relationship to the destination's first composition;
- rapid repeated navigation, interrupted transitions, back/forward, direct-load equivalence, keyboard activation, touch/mobile behavior, and reduced-motion/failure fallback when observable.

Do not navigate into purchases, submissions, authentication, downloads, or another consequential action merely to test a transition. Prefer ordinary editorial/navigation links. If a site is one page, performs hard reloads, exposes no safe route pair, blocks automation, or makes a state impossible to reproduce, record the absence or limitation instead of inventing behavior.

Maintain one sequence record per distinct mechanism:

| Mechanism / route pair | Entry or trigger | Initial/outgoing state | Wait/swap behavior | Incoming/final state | Duration/easing character | Desktop/mobile/keyboard/reduced/failure observations | Reusable principle | Evidence status |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Example case-study navigation | Project link activation | Image/title remain while page dims | Shared background bridges route readiness | Destination hero media and title reveal in order | Observed, not library-inferred | Mobile uses a shorter opacity path; reduced motion `UNVERIFIED` | Preserve subject continuity without a blank frame | Direct observation |

Separate a real loading dependency from an intentionally paced animation when evidence permits; otherwise mark the relationship as inferred. Never claim the reference uses ReactWP, GSAP, Barba, Swup, the View Transitions API, a shader, or client routing solely from the visible result.

### 3. Exercise interaction triggers

Test every distinct safe, reversible interaction that can affect the selected scope. Site-wide work covers the public interaction system; page- and component-level work cover relevant local interactions and their immediate dependencies:

- **Hover/pointer:** primary and secondary navigation, logo, text links, buttons, cards, images, galleries, project tiles, icon controls, cursor states, underlines, masks, overlays, captions, color shifts, zoom/crop, displacement, video preview, and pointer-following media.
- **Click/tap:** hamburger open/close, dropdowns, submenus, accordions, tabs, modals, drawers, lightboxes, media controls, carousels, filters, pagination, language selectors, dismissible notices, and route transitions.
- **Scroll:** viewport entrances, scrubbed timelines, pinned regions, horizontal sections, sticky layers, counters, text splitting, image sequences, parallax, progress indicators, and direction-dependent header changes.
- **Drag/swipe:** carousels, galleries, sliders, before/after controls, draggable canvases, maps, and inertia/bounds behavior.
- **Keyboard/focus:** tab order, focus-visible treatments, Enter/Space/Escape behavior, menu focus containment/restoration, and skip/navigation behavior.
- **Touch/mobile:** tap equivalents for hover-dependent information, mobile menu states, swipe gestures, viewport chrome, orientation, and coarse-pointer differences.
- **System state:** reduced-motion behavior when observable, loading/slow media, resize, repeated open/close, interrupted animation, and navigation back/forward.

Do not submit contact/newsletter forms, create accounts, authenticate, purchase, upload, or cause another meaningful external/state change merely to study an inspiration. Record the untested terminal action unless the user explicitly authorizes it.

For each distinct interaction, record:

| Element/location | Trigger | Initial state | Visual/spatial change | Timing/easing | Scroll/input coupling | Mobile/keyboard/reduced-motion equivalent | Reusable principle |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Example project image | Pointer enter/leave | Cropped still | Scale, caption reveal, cursor label | Observed duration/ease | Pointer position | Tap/focus behavior | Media feedback without hiding the title |

Distinguish what was directly observed from what is inferred. Do not claim a library, GSAP plugin, shader, or implementation technique solely from appearance.

### 4. Measure the visual system

Record decision-relevant relationships, responsive behavior, and computed values within the selected scope when browser inspection makes them available:

- font families, fallbacks, sources, variable axes, weights, styles, casing, display/body roles, and licensing constraints;
- font sizes across viewport ranges, fluid `clamp()` behavior, line height, letter spacing, line length, wrapping, indentation, and scale ratios;
- page/grid width, column count, gutters, outer margins, section height, block width/height, x/y alignment and offsets, z/layer relationships, overlaps, sticky ranges, borders, radii, and whitespace rhythm;
- image/video intrinsic and displayed dimensions, aspect ratios, crops, `object-fit`, masks, loading behavior, desktop/mobile substitutions, and pointer/scroll transformations;
- custom illustration and graphic systems: medium, motif, scale, crop, layering, labels, source/provenance, relationship to copy or data, interaction/motion, mobile transformation, and whether they explain, evidence, identify, orient, or only set atmosphere;
- navigation, logo, icons, buttons, cards, controls, and repeated block dimensions across states;
- colors, contrast roles, backgrounds, gradients, textures, blend modes, shadows, and theme changes;
- motion distance, origin, duration, delay, stagger, easing character, scrub/pin relationship, interruption, and performance cost.

Do not treat one screenshot measurement as a universal token. Compare at least desktop and narrow mobile, and identify whether a value is fixed, fluid, breakpoint-driven, content-driven, or viewport-relative.

### 5. Keep evidence and coverage honest

Maintain a compact record per reference:

```text
Reference and inspection date:
Viewports/input modes:
Pages and unique templates visited:
Routes/states not verified and why:
Homepage full-scroll completed:
Interactions exercised:
Typography and spatial measurements:
Motion/trigger inventory:
Responsive transformations:
Accessibility/performance risks:
Principles worth transforming:
Protected/distinctive elements not to copy:
Changes since the previous inspection:
```

Screenshots or recordings can support the notes when available, but they do not replace interaction testing. If browser control cannot exercise a hover, drag, scroll sequence, viewport, or protected page, mark that evidence missing instead of guessing.

For each reference, capture only decision-relevant observations:

1. **Concept:** the one-sentence idea that makes the site recognizable.
2. **Hierarchy:** the primary focal point, reading order, density, and dominant action.
3. **Composition:** grid, alignment, overlaps, whitespace, cropping, rhythm, and section transitions.
4. **Typography:** role of display/body faces, scale contrast, line length, casing, and rhythm.
5. **Color/material:** palette roles, contrast, surfaces, texture, borders, gradients, blend modes.
6. **Motion:** entrance language, scroll relationship, duration, easing, continuity, and reduced-motion implications.
7. **Interaction:** navigation model, hover/focus behavior, cursor/touch assumptions, feedback, and discoverability.
8. **Media:** photography, 3D, video, illustration, art direction, aspect ratios, and performance cost.
9. **Responsive transformation:** what reflows, disappears, becomes scrollable, or changes hierarchy.
10. **Risks:** accessibility, readability, performance, maintenance, browser support, and CMS resilience.

Also classify the reference's **container grammar**: which content is unframed, divided only by whitespace/rules, attached directly to media, grouped as a row/list/table, or enclosed in an actual surface/card. Record why each enclosure exists and whether it changes interaction, hierarchy or grouping.

Classify its **interface-device presence and absence** as well. For every active reference, record whether and how it uses buttons versus text links, contextual pretitles/uptitles/kickers, visible labels, item numbering, badges/status/tags, standalone trailing emphasis/fact lines, literal code/data, panels/cards/surfaces, and divider/metadata systems. `Absent` is a useful observation, not a missing note. Distinguish a required form label or application control from decorative editorial chrome.

Do not omit relevant behavior to save context. Organize repeated observations compactly and emphasize the patterns that should affect this project.

## Build an Influence Map

Before implementing a reference-led page, translate inspiration into an explicit map:

| Local area | Reference principle | Transformation for this project | Constraint |
| --- | --- | --- | --- |
| Hero | e.g. editorial asymmetry | Apply an offset 12-column composition to the supplied headline and media | Keep CTA visible and heading readable at 320px |
| Preloader / first reveal | Name the observed cold/warm entry sequence, content/font/media readiness behavior, exit and deliberate absence/limitations | Define the ReactWP Loader/critical-asset principle to transform or document why immediate styled rendering is stronger | No FOUC/FOUT, arbitrary delay, inaccessible trap or guessed implementation; preserve failure and reduced-motion completion |
| Page transition | Name the observed route pair and leave/wait/swap/enter continuity principle, including mobile/back-forward/interruption evidence | Translate the principle through ReactWP PageTransition/Loader/Scroller ownership or deliberately use immediate navigation | Preserve destination readiness, scroll/focus, input, interruption, failure, reduced motion and direct-load equivalence |
| Header | Name the inspected reference and its observed identity/navigation/menu/scroll principle | Transform that principle around the project's real logo, routes, actions and responsive needs | Preserve landmarks, keyboard order, menu focus, `aria-current` and touch targets |
| Case-study grid | e.g. cinematic crops | Alternate aspect ratios from CMS metadata | Reserve dimensions and lazy-load below fold |
| Repeated services | e.g. open editorial sequence | Keep titles and summaries on the page grid; add a marker only if order or taxonomy matters | Maintain scanability, focus and touch targets |
| Media rhythm | Name observed media-led/text-led alternation, scale, crop, sequencing and full-bleed moments | Map supplied, pending, optional and intentionally omitted project media across the page | Preserve purpose, focal intent, mobile transformation, semantics, loading priority and honest placeholder status |
| Interface devices / intentional absence | Record observed action, label, index, badge, trailing emphasis/fact, code/data, panel/surface and divider grammar, including families absent from all active references | State which devices the real content/interaction requires, which are omitted, and any minimal project-specific divergence | Preserve semantic labels/controls; reject decorative invention and page-wide micro-interface density |
| Graphic / illustration | Name the inspected motif/media/content relationship that drives this graphic | State its project-specific role, source, transformed concept, medium, relationship to copy, responsive behavior and motion | Preserve truthful meaning, provenance, accessibility/reduced motion and originality |
| Motion | e.g. continuous vertical rhythm | Reuse one reveal language across sections | Immediate reduced-motion state; no scroll blocking |
| Footer | Name the inspected reference and its observed end-of-page/navigation/brand principle | Transform that principle around the project's real destinations, contact/legal content and final gesture | Preserve semantic grouping, focus, mobile order and honest content |

Use influence-map rows proportionally. Site-wide work includes `Preloader / first reveal`, `Page transition`, `Header`, `Footer`, `Media rhythm`, and `Interface devices / intentional absence`; page-level work includes the rows that affect that page plus its persistent shell context; component-level work includes only the component's local content, surface/device, media, state, and interaction decisions. An intentional absence is recorded when it matters to the selected scope. Add a `Graphic / illustration` row for each prominent custom graphic family in scope, or record the decision to rely on content, real media, typography, or whitespace when that is the stronger choice.

For an existing implementation, the influence map and delta ledger reference each other. The influence map explains the target principle; the delta ledger proves what must visibly change from the current rendered state. Do not duplicate them into drifting private versions.

## Synthesis Rules

- Give each reference a role. One can drive typography, another composition, and another motion; avoid averaging all references into an incoherent middle.
- Assign preloader/first reveal and page transitions explicit reference roles or an intentional absence. Transform the observed continuity and readiness principle through ReactWP's existing lifecycle; do not copy a distinctive curtain/mask sequence, impose a loader merely because a reference has one, or add latency so an animation can be seen.
- Scope every observed device to its actual role, context, frequency, scale, interaction, and responsive behavior. A single occurrence is evidence for that occurrence, not a blanket permission for a component family.
- Assign the header and footer explicit reference roles. Do not let the body receive all of the observed art direction while the shell falls back to a starter pattern.
- Assign prominent graphics an explicit role and a driving source. Reference influence must alter their motif, medium, scale, crop, relationship to content, rhythm, or behavior—not merely their colors or easing.
- Translate the inspected media cadence into a project media plan. If an asset will arrive later, keep the intended proportion and page rhythm with a clearly pending placeholder instead of shrinking the media moment, substituting generic artwork, or turning the section into another text panel.
- Let observed absence constrain invention. If none of the driving references uses a device family, do not add it unless a real content, state, order, control, or interaction need survives the removal test; document that divergence before implementation.
- Choose one dominant concept for the page. Supporting effects must reinforce it.
- Translate visual tricks into reusable rules: a spacing ratio, crop system, type scale, motion curve, or component state.
- Adapt reference patterns to the actual WordPress content model. Design for long titles, missing images, optional sections, rich text, and variable item counts.
- Preserve the project's own brand assets and content. If brand direction is missing, create a restrained system that can be tuned rather than inventing an unrelated identity.
- Awwwards interaction is often desktop- and pointer-led. Supply keyboard, touch, reduced-motion, and narrow-layout equivalents.
- Prefer one memorable interaction executed well over many unrelated effects.
- If a reference conflicts with accessibility, performance, or the user's functional goal, keep the underlying intent and redesign the mechanism.

## Avoid Generic AI Component Grammar

### Cards and surfaces

A card is a semantic and interaction choice, not the default shape for a component. Use one when content is a genuinely discrete object, the surface clarifies grouping or clickability, repeated objects benefit from comparison, or the active reference/product system provides clear evidence for it.

Before creating a card, answer:

1. What content boundary or interaction does the enclosure communicate?
2. What directly observed reference or product rule supports a surface here?
3. Would hierarchy, comprehension, navigation or state become worse if the border/background/radius disappeared?
4. Is the repeated item truly a reusable object, or is a row, list, editorial block, media-caption pair, table, timeline, accordion, full-width band or open-grid composition more appropriate?
5. How do real short/long/missing content and media create meaningful variation without breaking consistency?

Watch for the combined pattern commonly read as AI-generated design:

- three or four equal rounded rectangles used regardless of the content count;
- identical padding, radius, border and soft shadow on every section;
- an icon inside a colored circle above an eyebrow, title, short paragraph and generic CTA;
- floating translucent panels over gradient blobs or dark backgrounds without content-driven purpose;
- every object centered, vertically stacked and equal-height;
- nested cards, pill badges and decorative metrics added mainly to make empty space feel “designed”;
- repeated marketing copy lengths and placeholder-like claims that make unrelated content look interchangeable.

Do not invent statistics, testimonials, ratings, client logos, awards, people/avatar stacks, badges, feature claims or icons merely to complete one of these patterns. Use verified project content and available assets; let absence produce honest whitespace or a different structure, and coordinate any needed copy/media with content/SEO.

None of those details is individually forbidden. Their unsupported combination is a warning that the result came from a remembered template rather than the inspected references and actual content.

Prefer the structural alternatives evidenced by the project: open sections separated by meaningful rhythm, asymmetric editorial grids, rows, image-led sequences, typographic lists, full-bleed moments, split text/media fields, overlapping layers, timelines, tables, accordions, marquees or intentionally varied modules. Add indices and rules only when their semantics or the observed reference requires them. Do not add novelty for its own sake; choose the structure that communicates the content best.

If an active reference genuinely uses cards, inspect its exact reason and behavior: density, proportion, edge treatment, media crop, typography, hover/focus state, surrounding whitespace, responsive transformation and relationship to non-card sections. Transform that system deliberately instead of reducing it to a generic rounded rectangle.

### Robotic annotation and over-segmentation

AI-generic work is not limited to cards. Audit the page for a repeated micro-interface layer that makes editorial content resemble a dashboard, component showcase, technical specification, or generated agency concept regardless of the subject.

Common combined symptoms include:

- a tiny uppercase, widely tracked, or monospace kicker before nearly every heading;
- a pretitle/uptitle or generic “section label” inserted only because the component API exposes that field;
- decorative numbering on cards, rows, features, sections, or steps whose order has no meaning;
- labels, pills, statuses, tags, anchors, and pseudo-code that restate nearby copy;
- a small bold, colored, uppercase, or monospace word/line appended after each description as an owner, category, technology, qualifier, or pseudo-conclusion even though the sentence is already complete;
- equal repeated panels whose small identifier, large title, short paragraph, borders, and empty area manufacture a component showcase instead of expressing a real object or interaction;
- real words presented as terminal commands, property values, or code merely to signal “technology”;
- hero footers and metadata rails split into equal cells containing interchangeable slogans;
- processes rendered as repeated equal boxes with arrows, plus signs, or connector lines even when no state, branch, or interaction is being explained;
- every content group separated by the same border-top/border-bottom grid and the same label-title-copy-detail columns;
- multiple hierarchy layers such as index + category + title + bold detail + code label when a heading and paragraph already carry the meaning.

Audit the function, not class names. For every compact annotation or enclosure, record its unique message and semantic role. Remove it when the adjacent content remains equally clear. Then review the complete page: if every section begins, divides, and ends with the same technical apparatus, redesign the rhythm instead of merely changing typeface, color, border, or selector name.

For reference-led work, also run the absence test: compare the local device family with the interface-device ledger. If every active inspected reference omits it, the proposal needs an independently necessary content/interaction role plus a documented minimal divergence. A desire for visual balance, another hover animation, or a more “finished” component is insufficient.

Legitimate uses remain legitimate. Actual source code may use `<code>`; real progress, chronology, instructions, rankings, or cross-references may need numbers; dashboards may need status; a genuine system diagram may need nodes and connectors. The observed reference and project content must determine density and treatment. Human specificity comes from meaningful omissions as much as additions.

### Generic graphic filler

Audit the purpose and source of every prominent illustration, diagram, animated SVG, canvas, 3D object, collage, data-like field, and decorative visual system. A graphic must provide evidence, explain a real relationship, establish a project-specific atmosphere or identity, or help navigation. “The hero needed something on the right” and “it makes the product look technological” are not valid roles.

Warning patterns include arbitrary combinations of concentric or orbit/radar rings, route lines, nodes, particles, grids, neon glow, floating interface fragments, generic device frames, and small technical labels. None is forbidden. They require direct support from real data or topology, the subject matter, an established brand language, or a transformed principle observed in an active reference. Labels must not be used to make an otherwise interchangeable abstract form appear meaningful.

Prefer real photography/video, people, places, archival or product artifacts, meaningful data, expressive typography, custom illustration grounded in the subject, or deliberate whitespace when these carry the story more honestly. Do not interpret “human” as automatic blobs, fake hand-drawn marks, random misalignment, noise, or simulated imperfection; specificity, authorship, content relationships, and restraint are the goal.

For each accepted graphic, document its art-direction brief: role; project evidence; driving inspected reference principle; transformed motif/material; medium; relationship to adjacent copy/media; desktop/mobile composition; interaction/motion and still/reduced-motion state; semantic equivalent or decorative status; asset provenance; and originality boundary. Motion must express the concept rather than defaulting to orbiting, pulsing, path drawing, or pointer following.

### Actions, header, and footer

Observe the reference's action and page-shell grammar with the same care as its hero and cards:

- button versus text-link usage, number and hierarchy of simultaneous CTAs, wording, geometry, fill/border, type, icons, hover/focus/active behavior, and mobile treatment;
- logo scale and placement, navigation density, menu trigger/open state, header transparency/stickiness/theme changes, and any utility content;
- how the last section enters the footer, footer depth and composition, navigation/contact/legal roles, typography, imagery, interaction, and the emotional end of the page.

Do not default to a filled capsule beside an outline/text control, append an arrow to every label, add magnetic motion everywhere, place ornamental “system ready” status in the header, or end with a shallow three-column metadata strip. None is forbidden; each needs semantic purpose and directly observed or project-specific support. Header and footer must participate in the same authored narrative as the body, not surround it with a generic starter shell.

Negative constraints are not enough. When header or footer is in scope, write its influence-map row before implementation and identify which observed structural and interactive decisions will be visible in the result. After implementation, compare each affected shell area against that row at representative desktop and mobile states. A color, font, radius, logo swap or generic menu animation alone does not count as reference influence.

Run a final genericity test:

- If the logo, brand color and images were removed, would the page be indistinguishable from a generic AI/SaaS template?
- Could the same component arrangement accept an unrelated company with only the nouns replaced?
- Did inspecting the references materially change the section architecture, or only decorative tokens?
- For an existing page, does the delta ledger show and the rendered result prove changes to the affected first viewport, section sequence, carrier/media rhythm, interface-device density, actions, shell, and end state—not merely rewritten documentation or visual polish?
- Is every cited reference device used in the same role/context and at a comparable frequency, scale and responsive/interaction state, or was an isolated occurrence cherry-picked from elsewhere in the pool?
- Does every major section have an intentional primary carrier, and do real/pending media or artifacts occupy the promised geometry instead of being replaced by generic decorative systems or collapsed into more text?
- Does every repeated visual wrapper still have a semantic or interaction reason?
- Does every kicker, eyebrow, index, badge, code treatment, metadata rail, divider or boxed step add information that would otherwise be lost?
- Does every panel/surface communicate a real boundary or behavior, or is it merely an equal frame for a small identifier, oversized title and paragraph?
- Does every standalone bold/colored trailing fact add a relationship the reader needs, or is it an ornamental final hierarchy layer that could be integrated into the sentence or removed?
- Did the implementation introduce any button family, pretitle/uptitle, visible editorial label, item number, badge, code treatment, panel, or divider system that all active references omit? If so, what necessary reader or interaction function justifies the divergence?
- If the compact annotation layer were removed, would the page become clearer and more specific rather than less understandable?
- Could the same button pair, header status treatment, and footer utility strip be dropped unchanged into an unrelated AI/SaaS site?
- Does the header have a named observed reference principle that changed its structure, navigation hierarchy, state behavior or mobile menu—not only its styling?
- Does the footer have a named observed reference principle that changed its transition, depth, content architecture, brand gesture, interaction or mobile reading order—not only its background color?
- Could any prominent graphic move unchanged to an unrelated AI, crypto, agency, or SaaS page after swapping its labels and brand color?
- If its labels disappeared, would the graphic still communicate a project-specific idea, or would arbitrary geometry remain?
- Was the graphic created because the content or concept required it, or merely because the composition had empty space?
- Did the inspected references materially change its motif, medium, scale, crop, content relationship, rhythm, or behavior rather than only its decorative tokens?

If the answer exposes genericity, revisit the influence map and redesign the composition before adding polish or motion.

## From Reference to Tokens

Convert observations into a small configurable vocabulary before building many sections:

```scss
:root{
    --color-canvas: #f4f1e9;
    --color-ink: #11110f;
    --color-accent: #d94b2b;
    --space-page: clamp(1rem, 3vw, 3rem);
    --space-section: clamp(5rem, 11vw, 11rem);
    --measure-copy: 68ch;
    --radius-media: 0.25rem;
    --ease-emphasis: cubic-bezier(0.22, 1, 0.36, 1);
}
```

These are examples of roles, not the default ReactWP aesthetic. Derive actual values from the user's content, brand, and selected references. Add a card/surface token only when the approved container grammar actually uses that role. Avoid importing a reference's exact palette or typeface without authorization and licensing clarity.

## Motion Translation

Describe motion as a system before selecting GSAP calls:

- **Purpose:** reveal hierarchy, maintain route continuity, explain spatial change, or provide feedback.
- **Vocabulary:** fade/translate, mask reveal, scale, shared element, scrub, pin, or text treatment.
- **Timing:** fast feedback, standard entrance, or long editorial transition.
- **Trigger:** route readiness, viewport entry, user action, or scroll progress.
- **Fallback:** immediate or restrained reduced-motion state.
- **Lifecycle:** creation, interruption, cleanup, and interaction with ReactWP loader/Scroller.

Then load only the relevant GSAP references. Do not select a plugin merely because the source site appears to use it.

## Originality Boundaries

It is acceptable to learn from:

- general layout grammar, pacing, hierarchy, or interaction categories;
- broad typographic contrast and spacing relationships;
- common UI patterns and motion principles;
- a combination of independently transformed influences.

Do not reproduce:

- logos, names, copy, brand marks, proprietary fonts, or media without permission;
- distinctive illustrations, icons, 3D objects, or photography;
- an unmistakably unique sequence of sections, composition, and animation with only content swapped;
- source code, shaders, or downloadable assets taken from the reference.

When a user explicitly requests a close reproduction, clarify which assets and rights they control, then still adapt interaction for accessibility and the ReactWP runtime.

## Deliverable Standard

For reference-led implementation, summarize only the evidence required by the selected scope and do not imply broader coverage. Include:

- the selected site/page/component scope, coverage record, inspection date, tested viewports/input modes, and anything left `UNVERIFIED`;
- for site-wide work, the homepage's complete scroll narrative, representative template coverage, persistent shell, and public interaction inventory;
- preloader/first-reveal and page-transition evidence only when those mechanisms are in scope or materially affect the studied experience, including observed-versus-inferred status and relevant mobile/reduced/failure behavior;
- the dominant design idea;
- for an existing implementation, the current rendered baseline, primary-carrier map, authoritative delta ledger, and visible before/after evidence for every affected major region;
- which reference informed which local decision;
- how each reference-supported device matches the local role/context, frequency/density, scale/adjacency, interaction/state, responsive behavior, and whole-page proportion rather than relying on its mere existence in the pool;
- the separate header and footer influence-map rows, observed evidence, desktop/mobile states, interactions, transformed decisions and originality boundaries;
- the separate `Preloader / first reveal` and `Page transition` influence-map rows, with the exact observed principle, ReactWP transformation or intentional omission, and accessibility/performance/originality boundaries;
- the `Media rhythm` row and asset-status inventory, including supplied/pending/optional media, purpose, expected subject, format, scale/ratio, focal/crop intent, full-bleed moments, text relationship, responsive behavior, loading priority, and placeholder/replacement plan;
- the `Interface devices / intentional absence` row and ledger, including observed absences, semantic necessities, omitted presentation devices such as standalone trailing emphasis/fact lines, and every approved minimal divergence;
- each prominent graphic/illustration influence-map row and art-direction brief, including project evidence, transformed reference principle, content relationship, responsive/motion behavior, semantics, provenance and originality boundary—or the recorded decision to use no decorative graphic;
- the resulting container/annotation/action/shell grammar and the justification for every repeated card, compact label, index, technical treatment, divider, metadata rail, boxed process, action treatment, header, or footer pattern;
- what was intentionally changed or omitted;
- how the concept transforms on mobile and reduced motion;
- the main accessibility and performance safeguards.

The implementation should feel related to the references at the level of taste and principle, while remaining recognizably its own product.
