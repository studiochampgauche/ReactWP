Manage legal documents, cookie consent, and consent-aware analytics or marketing integrations from one portable WordPress plugin.

== Description ==

Universal Legal Pages adds a dedicated "Legal pages" area to the WordPress administration. Each document uses the native WordPress title, editor, revisions, publication workflow, and page permissions.

Published documents receive an address under `/legal/document-slug/` and use the plugin's own full-page PHP template. The document header displays its localized WordPress last-modified date in semantic `<time>` markup. The active theme header, footer, React application, ACF, and ReactWP runtime are not required. Queued theme/plugin styles and scripts are removed from this route, except WordPress's logged-in admin-bar assets, so the result stays visually and functionally isolated when the plugin is moved between sites.

The "Consent" submenu adds a portable cookie banner and preferences dialog. Administrators freely choose which published legal documents appear as links in both interfaces; this selection never changes a theme menu. They can also create, rename, reorder, or remove consent categories in one ordered registry. A fresh registry contains only the strictly necessary category, which remains first and cannot be removed; every optional category exists only after an administrator creates it. When that required category is the only available choice, the preferences dialog omits its Reject all action because nothing optional can be refused. A category is a visitor-facing group with a stable ID, name, and description, and its assignment alone controls whether an integration is always active or requires a visitor choice. The administration never asks for a second privacy-behavior value. Built-in adapters still retain their reviewed internal Google or vendor signal mapping. When ReactWP supplies its Site settings languages, each language has its own category copy, ordered document selection, and ordered explicit-confirmation documents. With JavaScript available, the form saves through an authenticated, nonce-protected WordPress AJAX action without reloading the screen. A fixed, dismissible live notice reports the pending, successful, or validation-error state from anywhere in the long form. The native Settings API submission and complete WordPress notice stream remain as the no-JavaScript fallback. The interface runs in an isolated Shadow DOM, stores a versioned first-party consent cookie, respects Global Privacy Control when enabled, and exposes individual services separately, so accepting YouTube does not authorize Google Analytics.

The plugin interface follows the WordPress locale. English is the source and fallback language, while complete `fr_CA` and `fr_FR` catalogues provide French administration and public defaults. The browser manager uses the same English defensive fallbacks, so a WordPress locale without a plugin catalogue displays English rather than French. Each settings-section header previews the controls in its paired body, including renewal, GPC and revisit behavior; localized interface text; editable categories; detected-resource limits; ordered legal links and explicit acceptance; and built-in or custom integrations. The complete consent-interface copy uses the same two-column **Consent interface** settings section as detected services, consent links, and integrations: its title and description remain on the left while the language editor remains on the right. Every settings section shares the Integrations section's vertical inset, including after the layout stacks on narrow screens. ReactWP languages appear directly as tabs, without redundant language-source notices, above five concise native accordion groups. Every group starts closed, its summary explains the contained copy, and opening one group closes the previous group. Inside a group, every labelled copy unit occupies the full editor width and units always stack vertically, at every viewport width. Category names and descriptions live in the separate Consent categories section, where each card contains only clear visitor-facing copy and compact per-language tabs. The service copy group covers its heading, description, blocked-content message, allow button, and unclassified state. When the plugin detects ReactWP and its valid Site settings language list, the administrator writes the complete interface and category copy and selects the consent links for each configured language. The current ReactWP route language selects all three public bundles, including during client-side navigation. In Consent module links, the language tabs begin directly with the ordered displayed pages; a dedicated explicit-acceptance fieldset follows them and keeps the global toggle above an ordered list of confirmations. Every confirmation is one card, has one legal document per ReactWP language behind a compact tab rail, and can be added, removed, or moved with accessible controls. On every other WordPress site, the same sections edit one portable copy bundle, one category-copy set, one global link selection, and one ordered confirmation list with no ReactWP or multilingual dependency.

Each explicit-acceptance checkbox, confirmation label, and legal link shares one natural text baseline, so the inline link cannot make the label artificially tall or shift the checkbox out of alignment.

Built-in adapters understand:

* Google Analytics 4 as an analytics integration.
* Google Tag Manager as an analytics/marketing container using Google Consent Mode v2 signals.
* Google Ads as a standalone standard-remarketing integration when GA4 or Tag Manager is not used.
* Meta Pixel as a marketing integration.

The same screen can store up to 12 custom integrations without editing the plugin. Each one has a public service name, one consent-category assignment, one absolute HTTPS script URL, and optional initialization JavaScript. "Not selected" stores the definition without exposing or executing it publicly. Assignment to Necessary loads it as required site code without asking the visitor; assignment to any other existing category makes it an individual visitor-facing service choice that is requested only after acceptance.

Published WordPress content and oEmbed output are inspected at the end of their normal filter pipelines for external HTTP(S) iframes. Valid YouTube `/embed/{id}` URLs are rewritten to `www.youtube-nocookie.com`; valid Vimeo player URLs and other external iframes are replaced by declarative placeholders without an executable `src`. YouTube and Vimeo have reviewed dormant adapters, but they are not public services by default. When an administrator views affected content, every recognized or unknown service is recorded as unclassified and remains blocked without a visitor allow action. It appears in visitor preferences only after the administrator explicitly names it and assigns one existing consent category. The quote-aware scan is bounded to 1 MiB and 64 URL candidates; ambiguous tags, duplicate sources, `srcdoc`, malformed closures, oversized iframe-bearing content, or excess candidates fail closed rather than leaving remote iframe markup executable.

When a user with `manage_options` visits an administration or public page, the plugin inventories up to 200 queued WordPress scripts. It stores only the bounded WordPress handle, canonical host, kind, and managed state—never the external path or query—and never stops or replays those scripts. Reporting-only scripts remain admin-only and do not enter the public registry, hash, cookie, or visitor controls even after classification. Trusted project code must remove the eager loader, publish a reviewed `managed: true` service definition, and provide its adapter before the plugin can control it. The non-autoloaded detected registry and the public service list are both limited to 32 services, and storage is updated only when the canonical inventory changes.

The built-in adapters use a basic consent-mode approach: each administrator-assigned category gates the integration, while the adapter retains its fixed internal Google or vendor signal mapping. Their category selectors start at "Not selected"; an identifier may be saved in that state, but it is omitted from active public configuration and no vendor request can occur until a category is selected. Necessary loads the adapter immediately; every other category waits for its category or individual service choice. GA4 and the standalone Google Ads destination share one Google tag loader when both are configured. No private API key or account password is stored by the plugin. The measurement, container, advertising, and pixel IDs are publishable browser identifiers only after activation through a category assignment.

The plugin does not delete legal documents or consent settings when it is deactivated or removed. Deactivation unregisters the post type before refreshing rewrite rules so the `/legal/` permastruct does not remain stale.

== Installation ==

1. Copy the `universal-legal-pages` directory to `wp-content/plugins/`.
2. Activate "Universal Legal Pages" in the WordPress Plugins screen.
3. Open "Legal pages" in the WordPress administration and publish the required documents.
4. Open "Legal pages > Consent", link the published documents, enter the integration IDs, and enable the banner.

Activation refreshes WordPress rewrite rules once. If a site changes the public slug later, visit Settings > Permalinks and save once.

== Consent contract ==

The browser cookie uses the site-partitioned base name `ulp_consent_{blog_id}`. On HTTPS, the manager hardens the effective name to `__Host-ulp_consent_{blog_id}` and forces `Secure; Path=/` without `Domain`, preventing a sibling subdomain from planting an accepted consent cookie. Plain HTTP keeps the base name and configured WordPress path only for local or legacy compatibility; do not enable optional production integrations without HTTPS. The exact schema-v4 cookie stores the consent schema version, policy version, service-registry version, an exact boolean map keyed by the current category IDs, compatibility projections derived from accepted service behaviors, one boolean for every activatable service, one aggregate boolean proving that every currently configured explicit confirmation was checked, Global Privacy Control state, and an ISO timestamp. Necessary and unclassified services are not stored as granted. It also uses `SameSite=Lax` and an expiry, and does not contain a name, account ID, IP address, or other user profile.

The default duration is 180 days and can be configured from 30 to 365 days. Change the policy version whenever the purposes, vendors, or legal terms materially change; a version mismatch makes the old cookie invalid and presents the banner again. While explicit acceptance is active, changing the ordered confirmation-document registry also changes `serviceRegistryVersion` and automatically invalidates the previous choice.

Necessary consent is always enabled. Up to 16 categories may exist, including the required one. The selected category is the complete administrative loading rule: Necessary services and integrations are always active, every other category requires the visitor's choice, and unclassified services are never activable. No separate privacy-behavior field is submitted for a persisted custom integration. Reviewed built-in and project adapters may still carry an internal purpose used only for vendor consent signals and Global Privacy Control. Google receives denied defaults locally before any optional Google network request. An accepted site-preferences service controls `functionality_storage` and `personalization_storage`; audience-measurement services control `analytics_storage`; advertising/marketing services control `ad_storage`, `ad_user_data`, and `ad_personalization`; necessary security storage remains granted. When Global Privacy Control is respected and active in the browser, optional advertising/marketing services and integrations remain denied, while anything deliberately assigned to Necessary remains active. Revoking a previously accepted category or service sends the available vendor revocation signals, removes known first-party vendor cookies on a best-effort basis, and reloads the page so the adapter is no longer loaded.

The Google Tag Manager container is requested only after its administrator-assigned category has been accepted. Its Google Consent Mode v2 defaults and current service-derived update are queued before the container starts. Google tags can therefore use their built-in consent checks, but every non-Google or custom tag in the container must still declare its own consent requirements and triggers. A container can bypass the site's choice if it contains an unrestricted custom tag.

The standalone Google Ads field accepts a publishable ID in the canonical form `AW-` followed by 5 to 20 digits. It loads the Google tag and configures that destination only after marketing consent, which supports standard website-visitor remarketing without GA4 or Tag Manager. It does not create a conversion label or dynamic-remarketing event data; those events and business parameters must be implemented for the specific project. Do not configure the same Google Ads destination both directly and inside Tag Manager.

All available published legal pages can be selected for the consent interfaces and ordered by drag and drop or keyboard-accessible move buttons. The editor presents the full-width displayed-pages list first, followed vertically by a separated full-width list of remaining published pages. The chosen order is stored as unique positive WordPress IDs, preserved in the public banner/preferences links, resolved again against the public `legal_page` type and publication state, and exposed to the browser only as title/HTTP(S) URL pairs. Empty selection is valid. A non-user-facing ceiling of 1,000 entries bounds malformed requests and public payload work without imposing the former 20-page product limit. Standalone WordPress stores one global selection. ReactWP stores one exact selection and one ordered confirmation-document list for every configured language; every language must contain the same number of confirmation entries so cards stay aligned during a route-language change. Malformed multilingual input preserves the complete previous map. Existing global and older fixed privacy/cookies/terms selections are duplicated across the configured languages until the multilingual fields are first saved.

The optional explicit-acceptance module supports up to 50 ordered confirmation documents. Each document is linked directly beside its own required checkbox and does not need to be part of the general link list. The public browser configuration exposes the complete ordered `termsLinks` array and retains `termsLink` as a first-item compatibility projection. The visitor cannot save optional choices until every configured confirmation is checked; the cookie stores one aggregate `terms: true` value rather than personal or per-document evidence. In ReactWP mode, explicit acceptance can be enabled only when every configured language has a published document at every confirmation position. It is not an authenticated signature, an immutable audit trail, or sufficient evidence for a high-value contractual transaction. Capture acceptance again in the relevant authenticated form or transaction when legal proof is required.

Every legal document link rendered by the consent banner, preferences dialog, or explicit-acceptance control opens in a separate browser tab with `noopener noreferrer`, preserving the visitor's current consent state without exposing an opener relationship.

The plugin controls integrations loaded through its built-in adapters, persisted custom integrations, managed iframe placeholders, or its registration APIs. It cannot retroactively block analytics or advertising scripts that a theme, another plugin, or a Tag Manager container already fires without consent. Script inventory is reporting-only. Remove duplicate snippets, implement a trusted adapter for a reported script, and configure every Tag Manager tag with the appropriate consent requirements.

This plugin supplies technical consent controls, not jurisdiction-specific legal advice or automatic legal compliance. Review the wording, purposes, retention, vendors, and required choices with the site's legal or privacy adviser.

== Editor contract ==

The editable legal-page values are WordPress core fields:

* Title: canonicalized to plain text through `wp_insert_post_data` before every `legal_page` insert or update, then rendered as escaped text. WordPress permits an empty title, in which case the public H1 falls back to the translatable label "Legal document".
* Content: optional rich text constrained with `wp_kses_post()` through `wp_insert_post_data` before storage. This applies to the block editor, REST requests, imports, and other WordPress insertion paths, so headless consumers do not receive executable markup from the stored field. The standalone PHP template still passes the stored value through the standard `the_content` pipeline and applies `wp_kses_post()` again at its final HTML output boundary.
* Publication and revisions: owned by WordPress core using page capabilities. The plugin registers no custom mutation endpoint.
* Last modified date: read from WordPress's `post_modified` value, formatted with the site's localized date format, and exposed through an escaped machine-readable `<time datetime>` value.

Only published documents are publicly available through the normal WordPress singular query. Draft, preview, edit, revision, and deletion permissions remain governed by WordPress.

Password-protected documents keep WordPress's native password form through a dedicated narrow HTML allowlist for its form, alert, label, and input markup, including core accessibility and native validation attributes. Their stored legal text is not passed to the public content filters or rendered until WordPress accepts the password.

Consent settings are stored in the `universal_legal_pages_options` WordPress option and require `manage_options`. Both the authenticated AJAX path and the native Settings API fallback submit the exact version-2 settings contract. The complete transport is bounded to 4 MiB and uses a mode-aware top-level allowlist: standalone WordPress and ReactWP multilingual forms have their own required field sets, while executable custom-integration fields are accepted only when the current administrator also has `unfiltered_html`. Unknown, missing, outdated, oversized, malformed, or invalid fields reject the complete submission and preserve the previous option atomically. On the AJAX path, the plugin reads the canonical option back after the write; a mismatch returns `settings_persistence_failed` and is never reported as a successful save.

The complete public interface copy is editable: banner title/message, legal-navigation name, six action labels (including the permanent cookie button), preferences-dialog title/description, service copy, terms confirmation copy, GPC notice, and errors. These values, category names and descriptions, and public service names are non-empty plain text with field-specific Unicode limits. Submitted HTML is rejected rather than treated as display markup, and every accepted value is escaped again or assigned through a text-only DOM sink when rendered. On a standalone WordPress site, the exact nested `consent_strings` bundle is edited once. When both the ReactWP runtime and its `rwp_admin_langs()` capability are present, up to 32 unique validated Site settings languages activate the complete `consent_string_translations[language]` bundle instead. Every configured language and every required plain-text leaf must be present; malformed, incomplete, additional, oversized, or scriptable values emit `invalid_consent_strings` or `invalid_consent_string_translations` and preserve the complete previous bundle atomically. Descriptions use explicit bounds up to 600 Unicode characters and labels use their documented 80–160-character bounds. Legacy `banner_title`, `banner_message`, and `banner_translations` values are hydrated into the new complete contract without a write during reads, then retained as synchronized compatibility projections after a valid save. The current-language complete bundle is also copied into the portable fallback so the plugin remains usable if ReactWP is later removed. Invalid or oversized ReactWP language data falls back to the standalone contract rather than partially enabling multilingual behavior. Standalone WordPress uses the optional ordered `consent_page_ids` and `terms_page_ids` fields. ReactWP instead requires one exact `consent_link_translations[language]` bundle containing `consent_page_ids` and `terms_page_ids` for every configured language. General page lists are bounded to 1,000 IDs; confirmation lists are bounded to 50, require a deliberate presence marker, and must have contiguous positions and equal counts across languages. All entries are unique positive published `legal_page` IDs. Malformed, incomplete, additional, duplicate, sparse, foreign/unpublished, or oversized values emit `invalid_consent_link_translations` or `invalid_terms_page_ids` and preserve the previous atomic value. The legacy scalar `terms_page_id` is hydrated as a one-entry list and remains a first-item compatibility projection after valid saves. IDs are public references, not secrets, and final link labels and HTTP(S) URLs are resolved from WordPress rather than accepted from the request. Public link labels are normalized as plain text and limited to 200 Unicode characters before entering the browser contract. The optional `google_ads_id` field is plain text, is empty when disabled, accepts only `AW-` followed by 5 to 20 ASCII digits, is canonicalized to uppercase, and emits the stable `invalid_google_ads_id` Settings API error when malformed; the previous valid value is then preserved. Like the GA4, GTM, and Meta identifiers, it is intentionally public in the browser configuration and must never contain a secret.

Consent categories use one ordered `consent_categories` registry with at most 16 exact records. A fresh registry contains only `necessary`; it must be the first record and cannot be removed. Preferences, analytics, marketing, external-content, or any other optional group must be created explicitly. Every optional built-in-compatible or `category-{16 lowercase hex}` custom identifier may be edited or removed. Standalone submitted records contain exactly an ID, a non-empty plain-text label of at most 80 Unicode characters, and a description of at most 300. ReactWP submitted records instead contain the ID and those two leaves for every configured Site settings language. A technical-purpose field is not accepted on a category. Missing, additional, duplicated, sparse, scriptable, oversized, or structurally invalid data emits `invalid_consent_categories` and preserves the complete prior registry atomically. Existing stored categories and older fixed category copy are migrated in memory without silently deleting prior configuration. Category IDs participate in `serviceRegistryVersion`, so adding or deleting a choice invalidates older consent; display-only translations and order changes do not.

Persisted custom integrations require both `manage_options` and `unfiltered_html`, because `init_code` is the consent settings' only intentional exception to the plain-text/no-executable-markup rule. It is trusted public application JavaScript, not formatted copy. A user lacking either capability can save other consent settings without changing the existing custom list. The submitted list is an atomic replacement: it contains at most 12 contiguous exact records with `id`, `label`, `category`, `script_url`, and `init_code`; a deliberate empty list removes all custom integrations, while a missing or malformed transport preserves the prior list. Labels are non-empty plain text of at most 80 Unicode characters. `category` is either empty for the explicit "Not selected" state or references any existing category ID, including `necessary`. An empty category keeps the complete definition in administration but excludes its service and executable payload from public configuration. `necessary` makes the integration always active; every other category makes it consent-gated. Legacy stored records containing a valid `purpose` are read for compatibility, but the value is discarded from the canonical shape and is never accepted from the current form. Script URLs are unique absolute HTTPS URLs of at most 2,048 bytes with one canonical host and no credentials, whitespace, backslashes, or fragment. Initialization code is valid UTF-8 without NUL and at most 8,192 bytes. The complete custom public payload remains below 128 KiB. Any invalid type, unknown or nested field, sparse index, duplicate ID/URL, collision, oversized value, insecure URL, or non-empty missing category reference emits `invalid_custom_integrations` and preserves the complete previous list.

Custom script URLs and initialization code are emitted to every visitor as public browser configuration. They must contain only public identifiers—never passwords, private keys, bearer tokens, private download URLs, or server credentials. The browser independently validates the exact service ID, assigned category, unique canonical hostname, URL and size bounds before registration. It creates no optional custom script node before individual consent; a Necessary custom integration is intentionally created during initialization without waiting for a cookie. After an optional grant, it requests the external script, waits for its load event, then appends the stored initialization value to one script node through `textContent`; a network failure runs no initialization and permits a later retry. Changing any custom definition value, including its display label, changes `serviceRegistryVersion`, invalidates the old cookie, and requests a new choice before changed optional code may load.

Detected-service settings use the exact main-option shape `services[service_id][label|category]`. At most 32 entries are accepted. IDs must match `[a-z0-9][a-z0-9._-]{0,63}`, labels are non-empty plain text of at most 80 Unicode characters, and categories must reference the current category registry or the fail-closed `unclassified` sentinel. Detection alone is an administrator-only inventory event: an unclassified entry is excluded from the public registry, preference dialog, consent cookie, and allow controls. Assigning a real category is the administrator's explicit approval to publish that managed service to visitors. The two submitted leaves are the complete writable-field map: domains, kind, managed state, script handles, integration IDs, and any unknown or nested field are rejected. Those protected relations are derived from the separately detected registry. A malformed service map emits `invalid_services` and preserves the complete previous service configuration atomically. Deleting a category while a detected service or custom integration still references it preserves the prior category registry and emits `category_in_use`; reassign or remove those dependants in the same save.

The public `services` list contains only explicitly assigned predefined/custom integrations, detected managed services that an administrator approved with a real category, and valid managed definitions from trusted project filters. Unclassified and reporting-only inventory never reaches visitors. The list is sorted by ID and contains exact `id`, `label`, `category`, `purpose`, `domains`, `kind`, and `managed` fields. `purpose` is exactly `necessary`, `preferences`, `analytics`, `marketing`, or `external`; it is internal runtime metadata supplied by reviewed built-in/project adapters or safely derived from the assigned category, not a second administrator field. Kinds are exactly `integration`, `iframe`, `script`, `pixel`, or `unknown`. Configured GA4, Google Ads, and Meta identifiers create their respective managed services only when a category is selected; empty or unassigned identifiers create none. GTM remains container infrastructure rather than one service because its tags may span several purposes. `serviceRegistryVersion` is the first 24 lowercase hexadecimal characters of a SHA-256 hash over deterministically sorted service and category records plus the active ordered confirmation-document registry. Confirmation documents are omitted from the hash while explicit acceptance is disabled. Labels for ordinary detected/built-in services are excluded, so their display-only rename does not invalidate consent; a category/purpose/domain/kind/managed or active confirmation-list change does. For a persisted custom integration, its complete canonical definition—label, category, full URL, and initialization code—is also hashed so any edit requires a new visitor choice before different optional executable code may load.

== Integration API ==

Trusted project code can register an additional browser integration without editing the consent manager:

`window.UniversalLegalConsent.registerIntegration({ id: 'example', categories: ['analytics'], purpose: 'analytics', mode: 'all', load: function(consent){}, update: function(consent){} });`

Supported category values are every current category ID exposed by the public registry, including `necessary`; a removed ID is no longer accepted. An adapter whose complete gate is Necessary loads during initialization without waiting for a consent cookie. A definition may instead require one registered, managed `serviceId`; that individual service becomes the authoritative gate and supplies the adapter's internal purpose. If `categories` or `purpose` is also supplied with `serviceId`, it must match that service or registration fails closed. Without `serviceId`, a non-empty exact category list, one explicit internal `purpose` (`preferences`, `analytics`, `marketing`, or `external`), and the optional mode (`all` or `any`) form the gate. Unknown or duplicate categories, invalid purposes, and unknown modes reject the complete adapter rather than weakening its requirements. The `load` callback runs only after its gate is granted and is treated as loaded after a successful call. A thrown error or rejected promise permits a retry after a later consent change. The `update` callback receives later choices. Definitions registered before the manager initializes are queued automatically.

Trusted PHP can extend the service registry through the `universal_legal_pages_services` filter. The filter receives the complete public list and current normalized options, and must return at most 32 exact service records:

`add_filter('universal_legal_pages_services', function($services){ $services[] = ['id' => 'project-chat', 'label' => 'Project chat', 'category' => 'preferences', 'purpose' => 'preferences', 'domains' => ['chat.example.com'], 'kind' => 'integration', 'managed' => true]; return $services; });`

Invalid, duplicate, oversized, or unknown-shape filter output is rejected as a whole and the validated built-in/detected list is retained. This is trusted project code, not a browser registration surface; it must pair managed services with an actual reviewed loader/revocation adapter.

The public API also provides `getConsent()`, `hasConsent(category)`, `openPreferences()`, and `setLanguage(code)`. `setLanguage(code)` returns `true` and updates every visible and accessible interface string plus the legal and confirmation links in place when the code exists in the validated ReactWP translation maps, or when a regional code such as `fr-CA` has a configured primary-language entry such as `fr`; it returns `false` in standalone mode or for an unknown code. The banner, permanent cookie button, preferences popup, actions, categories, terms, GPC notice, errors, ARIA labels, ordered legal-link navigation, and every explicit-acceptance document change without recreating the dialog or losing the corresponding checkbox state. ReactWP calls it automatically when its route language changes, and an early call is retained until the manager initializes. A theme-owned button can open the same preferences dialog without inline JavaScript, including when the built-in permanent button is disabled:

`<button type="button" data-ulc-open aria-haspopup="dialog">Manage my privacy choices</button>`

The delegated trigger continues to work when the button is rendered after initialization or replaced during client-side navigation. Modified clicks on a link keep their normal browser behavior. The document emits `universal-legal-pages:ready` and `universal-legal-pages:change` CustomEvents with a copied consent detail object.

Custom adapters are trusted application code. They must use fixed reviewed vendor URLs, avoid secrets, define their real category requirements, handle revocation, and comply with the site's Content Security Policy.

Google, Meta, and custom scripts may require the final site's Content Security Policy and proxy/CDN headers to account for their reviewed domains. The built-in Google loaders request scripts only from `https://www.googletagmanager.com`; the final Google products can also require their documented collection and cookie domains in `connect-src`, `img-src`, or related directives. Meta Pixel requests its script from `https://connect.facebook.net`. If WordPress rewrites `plugins_url()` to an asset CDN, that reviewed origin must also be allowed by `style-src` for the Shadow DOM stylesheet. The WordPress bootstrap and public configuration are emitted as inline scripts, and dialog scroll locking changes the document's inline overflow style. Dynamically created custom external and initialization script nodes inherit a nonce already approved on the consent-manager script. Under CSP3, that approved nonce can authorize the configured external script without a matching host source and therefore explicitly delegates CSP trust to that exact administrator-configured URL; without such a nonce, its host must be allowed by `script-src`. The inline initialization also needs the inherited nonce or another compatible site policy. CSP or Trusted Types can still reject vendor code; do not solve this by enabling unrestricted `unsafe-inline`. Remote redirects and later vendor-file changes remain part of the selected supplier's trust boundary; the custom editor does not provide Subresource Integrity. A blocked or failed vendor script does not break the consent interface, but that integration will not run.

Revoking a custom integration turns its consent off and reloads the current page, but the plugin cannot know or reliably remove an arbitrary vendor's cookies, local storage, network state, or remote account data. Add vendor-specific cleanup in reviewed project code when required. Purge any full-page/CDN cache after changing a persisted integration so visitors receive its new registry version and configuration together.

== Customization ==

The default public base is `legal`. It can be changed before the post type is registered:

`add_filter('universal_legal_pages_rewrite_slug', function(){ return 'documents-legaux'; });`

The value is normalized as a WordPress slug. An empty or non-string value falls back to `legal`.
